# Deadlock and Steam sign-in: release note

This release adds **Deadlock** (discipline code `deadlock`) as the third installed game, with its data from
[deadlock-api](https://api.deadlock-api.com): the hero/map/mode catalog, a 66-tier native ladder, a batched rank
collector on the shared `rank` schema and a match decoder. It adds **Steam sign-in and account linking** (OpenID 2.0)
and the `steam` game provider. It also adds a game-neutral **match import by external id** (`stats.match_fetch`):
a captain or organizer names a tournament game's Deadlock match id, and `stats-worker` fetches and ingests it.

One database migration ships: **`deadlock01`** (after `drift01`). Run it, then deploy every backend service, the
gateway (route table and regenerated `schemas.json`) and the frontend **from one SHA**. Nothing is renamed or removed:
every wire change is additive (section 2).

## 1. What shipped

### 1.1 The Deadlock module (`backend/shared/disciplines/deadlock/`)

* **`SPEC`**: code `deadlock`, name and short name "Deadlock", icon `assets/deadlock/icon.png`, identity provider
  `steam`, registered in `shared.disciplines` after Overwatch and LoL. `.importlinter` lists
  `shared.disciplines.deadlock` in both forbidden lists.
  * Kinds: `character` "Hero", `map` "Map", `mode` "Mode". Character classes (deadlock-api `hero_type`): `marksman`,
    `mystic`, `brawler`, `assassin`.
  * Sides `hidden_king` (Team0) and `archmother` (Team1): labels only, no side-pick step anywhere.
  * One rated dimension `agent` with one role `agent` ("Agent"): Deadlock ranks are per player, not per position.
    Team-format preset `open_6v6` (6 starters, dimension mode `off`).
  * Stats (integers): `kills`, `deaths`, `assists`, `net_worth` ("Souls"), `last_hits`, `denies`, `level`
    (aggregation `max`), `player_damage`, `boss_damage`, `player_healing`, `player_damage_taken`. Event: `kill`.
  * Pick/ban preset `deadlock_hero_bans`: hero pool, per game 2 bans per team in the order A-B-A-B, ban lifetime 1
    game, 30 s per turn, a random hero on timeout (`random_fill`). The first ban rotates to the previous game's loser
    (`result_loser_first`); game 1 is opened by the higher seed. Organizers edit count and order in the rules editor.
  * `ingestors={"deadlock_api": decode}` and `match_fetchers={"deadlock_api": fetch_match}` (section 1.8).
* **Client** (`client.py`): every Deadlock read goes to `https://api.deadlock-api.com` through one
  `ResilientHttpClient` (15 s timeout, 3 attempts; the catalog sync uses 30 s and 2 attempts, because
  `/v1/assets/heroes` is about 1.9 MB). It sends `X-API-KEY` only when `DEADLOCK_API_KEY` is set.
* **Catalog sync** (`catalog_sync.py`, `POST /api/v1/admin/catalog-sync/deadlock`, superuser). Every deadlock-api read
  happens before the first catalog write. A source that times out, is unreachable or answers an error is **503
  `catalog_source_unavailable`** ("The Deadlock catalog source did not answer (ReadTimeout); try again in a minute"),
  for every game's sync, not a bare 500; run it again.
  * Heroes from `/v1/assets/heroes`, kept when `player_selectable` and not `disabled`. `in_development` heroes are
    **kept**, because private lobbies play them: live match 121244878 has hero 86, Violet. The code is `class_name`
    without `hero_` (`inferno` for Infernus); the slugified display name is an alias when it differs; the class is
    `hero_type`; `attrs.deadlock_id` is the numeric id match metadata names; the image is `icon_hero_card`.
  * One map, `midtown` ("Midtown"), and two modes, `normal` ("Standard") and `street_brawl` ("Street Brawl").
    deadlock-api has no mode art, so the map and both modes use the `/v1/assets/map` minimap image.
* **Decoder** (`ingest.py`, pure): deadlock-api `/v1/matches/{id}/metadata` bytes → `owt.match/1`.
  * `source.kind` = `deadlock_api`, `external_id` = the match id.
  * Teams `team0` and `team1`, placed from `winning_team`. The map is always `midtown`; the document carries no mode,
    because `MatchDoc` has no mode field.
  * A participant is keyed `p<player_slot>` (what `killer_player_slot` names) and identified as
    `{provider: "steam", id: "<account id>"}`.
  * Facts, each on the played hero (`entity` = the hero's catalog code, found by `attrs.deadlock_id`): the top-level
    `kills`, `deaths`, `assists`, `net_worth`, `last_hits`, `denies`, `level`, plus `player_damage`, `boss_damage`,
    `player_healing` and `player_damage_taken` from the last `stats[]` snapshot. A hero id no catalog hero carries is
    passed on verbatim, so the semantic validator reports it.
  * One `kill` event per `death_details` entry, the dead player as target.
  * A player with `account_id == 0` (anonymous) is **dropped** with its facts and every kill it took part in.
  * Bytes that are not match metadata → `DecodeError("invalid_metadata")`.

### 1.2 Ladder and native rank

* **Ladder** (`ladder.py`): 11 ranked tiers × 6 subranks = **66 tiers**, listed top first. deadlock-api reports a
  `badge = tier * 10 + subrank`. `rank_value = ((tier - 1) * 6 + subrank) * 100`, each subrank 100 wide:

  | Tier (number) | `rank_value`, subranks 1 … 6 |
  | --- | --- |
  | Eternus (11) | 6100–6599; Eternus 6 = 6600 and up (open top) |
  | Ascendant (10) | 5500–6099 |
  | Phantom (9) | 4900–5499 |
  | Oracle (8) | 4300–4899 |
  | Emissary (7) | 3700–4299 |
  | Ritualist (6) | 3100–3699 |
  | Mystic (5) | 2500–3099 |
  | Sentinel (4) | 1900–2499 |
  | Acolyte (3) | 1300–1899 |
  | Seeker (2) | 700–1299 |
  | Initiate (1) | 100–699 (Initiate 1 = 100–199) |
  | Obscurus (0, badge 0) | unranked, no value |

  * A ladder tier's slug is `<tier>-<subrank>` (`eternus-6`), its name "Eternus 6", `native_division` the tier name
    ("Mystic") and `native_tier` the subrank.
  * Emblems are `/disciplines/deadlock/ranks/<tier>.png`, one per tier; the subrank is shown as text.
  * Example: badge 102 → Ascendant 2 → 5600.
* **Grids:** a new Deadlock grid is seeded with this ladder, and a Deadlock tournament, mix or clone without a grid of
  its own falls back to it, like Overwatch and LoL.
* **Native rank** (`ranks.py`):
  * the source is the newest snapshot of each Steam account (one series per account: no role, platform or queue);
  * an account counts only if that newest row is ranked and its last successful poll is at most **30 days** old;
  * a player gets the best value across their Steam accounts, and that value stands for the one role `agent`.
* **Rank overview SQL twin:** `native_rank_rows` (`latest_rank_rows`, CTE `rank_native_latest_<game>`). `platform` is
  NULL.
* **Registration:** the autofill native stage reads this module's `native_ranks` like LoL's.

### 1.3 Deadlock rank collector

The collector runs in `stats-worker` as the module's jobs, when the worker serves `deadlock`. It is LoL's collector
with a **batched upstream**, on the shared `rank` schema: `discipline='deadlock'`, provider `steam`, `handle` and
`external_id` = the account id, `division` = the tier name, `tier` = the subrank.

* **Batching:**
  * a 60 s tick, leader-locked on `deadlock_rank:scheduler:leader`, claims up to `batch_size` (at most **1000**,
    deadlock-api's `account_ids` cap) due `rank.account_state` rows and publishes them as **one** fetch
    (`DeadlockFetchRequest{social_account_ids, source}`);
  * the consumer sends one `GET /v1/players/rank?account_ids=a,b,…` with no DB transaction open, then writes every
    account's outcome in one transaction, with one `fetch_log` row per account;
  * admin collect and registration approvals publish a player's Steam accounts as one batch on the priority queue.
* **Defaults** (`deadlock.rank_collection`): collection **on** (it needs no credentials), every **6 h** (21 600 s),
  `batch_size` 1000, scope `all`, auto-pace with jitter 0.15, 5 consecutive failures before `disabled`, backoff base
  60 s.
* **Rate limit:** `rate_limit_per_minute` counts deadlock-api **requests** (batches). Its default is derived, not
  stored: 20 without `DEADLOCK_API_KEY` (the per-IP limit) and 100 with it.
* **Scopes:** `all` (every Steam account) or `registrations_only` (the Steam accounts of members registered in an
  active Deadlock tournament, at priority tier 1).
* **Redis** (`deadlock_rank:*`): global cooldown `deadlock_rank:cooldown`, per-minute window
  `deadlock_rank:rl:<minute>`. There is **no** pending or in-flight dedup (section 8).
* **Queues**, each dead-lettering to `<name>.dlq`, declared by the module's `start_jobs`:

  | Queue | Fed by |
  | --- | --- |
  | `deadlock_rank_fetch` | The tick |
  | `deadlock_rank_fetch_priority` | Admin collect and registration approvals |
  | `deadlock_rank_registration_approved` | Routing key `tournament.registration.approved` |
  | `deadlock_rank_registration_rank_check` | Routing key `tournament.registration.rank_check_requested` |

  The two fetch queues share one channel with prefetch **1**: a batch is up to 1000 accounts in one request.
* **Outcomes:**

  | Outcome | Effect |
  | --- | --- |
  | A badge on the ladder | `ok`; a snapshot only when the rank changed; next poll after the interval |
  | Badge 0 or off the ladder | `ok`, unranked; an unranked row only when it ends a ranked series (a never-ranked account writes nothing) |
  | Account missing from the answer | `not_found`; next poll after 8× the interval; no row |
  | A handle that is not a Steam account id | Never sent upstream; `error` "invalid steam account id", exponential backoff capped at 6 h, `disabled` after `max_consecutive_failures` |
  | Failed batch (5xx, timeout, malformed JSON, transport error, open circuit) | Every claimed account deferred by `backoff_base_seconds`, no failure counted; one summary `fetch_log` row (no account, handle "batch of N") |
  | 429 | The same, plus a global cooldown of `Retry-After`, else 60 s |
  | Active cooldown or full per-minute window | The batch is deferred without calling upstream |

  Steam account ids never change: there is no PUUID re-resolution, region or rename.
* Fetch-log retention is 7 days (job `deadlock_rank_fetch_log_purge`, daily).
* **Rank routes:** every `rpc.stats.rank.*` route answers `?discipline=deadlock` through the module's 8
  `collection_handlers`, one series per account (no `queue`, `lp`, `wins` or `losses`).

### 1.4 Steam sign-in (identity-service)

* `SteamOpenIDProvider` (`provider_name = "steam"`) handles **login and link** through the existing OAuth callback and
  link paths. OpenID 2.0 has no client id or secret.
  * **Authorize:** `https://steamcommunity.com/openid/login` with `openid.mode=checkid_setup`,
    `openid.return_to=<OAUTH_REDIRECT>?state=<state>`, `openid.realm` = the scheme and host of `OAUTH_REDIRECT`, and
    `identifier_select` for `openid.identity` and `openid.claimed_id`.
  * **Callback:** Steam returns `state` and `openid.*` parameters and **no `code`**. The frontend callback page, when
    `code` is absent and `openid.mode` is present, forwards every `openid.*` parameter as the code (a query string)
    and continues the normal login or link flow.
  * **Exchange:** the provider accepts the assertion only when `openid.claimed_id` matches
    `https://steamcommunity.com/openid/id/<17 digits>`, `openid.op_endpoint` is the Steam login URL,
    `openid.return_to` starts with `OAUTH_REDIRECT?`, and `openid.signed` covers `op_endpoint`, `claimed_id`,
    `identity` and `return_to`. It then POSTs `openid.mode=check_authentication`, which must answer `is_valid:true`.
    The state nonce is single-use, and Steam verifies an assertion only once.
  * **User:** `provider_user_id` = `username` = the decimal SteamID3 **account id**. The persona name (`display_name`,
    falling back to the id) and the avatar come best-effort from deadlock-api `GET /v1/players/steam?account_ids=`.
    `raw_data = {"steamid64": …}`.
* The persona name is display text only. The stored handle and every ownership match use the account id, so a persona
  name set to someone else's id never reaches their player.
* `steam` is in `OAUTH_PROVIDERS` and `VERIFIABLE_PROVIDERS`. A completed Steam sign-in or link stores a **verified**
  `steam` `players.social_account` whose `provider_user_id` and handle are the account id.
* The provider is advertised only when `STEAM_OAUTH_ENABLED` is on and `OAUTH_REDIRECT` is set. Every provider is now
  enabled when its flag is on and every other setting it names is present; the other providers still need both
  credentials.
* The player self-link accepts a Riot or Steam connection. Its 400 detail is now *"Link Discord, Battle.net, Riot or
  Steam OAuth account before linking a player"*; the 403 detail is *"Discord, Battle.net, Riot or Steam account does
  not match selected player"*.
* Frontend:
  * `/auth/steam/login`, and Steam in the sign-in modal and the account-settings link buttons;
  * a notice beside those buttons that linking makes the Deadlock rank public (`accountSettings.linked.steamNotice`);
  * the admin provider mark (`providerSteam`) and the registration and identity icons (`/steam.svg`).

### 1.5 The `steam` game provider and its handle

* `SocialProvider.STEAM = "steam"`: label "Steam", order 7, text entry, OAuth, verifiable, game provider. Handle error
  key `identity.steam.format`; registration form builtin `identity_steam`.
* **The canonical handle is the decimal SteamID3 account id**, 1..4294967295 (what deadlock-api calls `account_id`).
  The normalize rule `steam_id` turns every accepted spelling into it, case-insensitively:

  | Input | Example | Account id |
  | --- | --- | --- |
  | Account id | `206464648` | itself |
  | SteamID64 (17 digits) | `76561198166730376` | id64 − 76561197960265728 |
  | SteamID3 | `[U:1:206464648]` | N |
  | SteamID2 | `STEAM_0:0:103232324` | Z × 2 + Y |
  | Profile link | `https://steamcommunity.com/profiles/76561198166730376/` | from the SteamID64 |

  Any 17-digit id whose account id falls in 1..2^32−1 is accepted, not only `7656119…`. A vanity
  `steamcommunity.com/id/<name>` link cannot be resolved offline and fails the pattern.
* The handle pattern spells the exact range 1..4294967295 out digit by digit, so an out-of-range number never
  reaches the collector's batched `account_ids=` query. The frontend mirrors it (`identity_steam`) and shows
  "SteamID64 or profile link" as the placeholder.
* The frontend profile link is `https://steamcommunity.com/profiles/<SteamID64>`.

### 1.7 Generic match import by external id

Stats core owns the mechanism; a module only declares a fetcher.

* **Module hook:** `shared/disciplines/ingest.py` adds `MatchFetcher = Callable[[str], Awaitable[bytes]]`,
  `MatchFetchNotReady` (retry later) and `MatchFetchFailed` (permanent). `DisciplineSpec.match_fetchers` maps a
  source kind to its fetcher (default empty). A discipline must declare exactly one to support import.
* **Table `stats.match_fetch`:** `id`, `discipline`, `source_kind`, `external_id`, `hint_tournament_id`,
  `hint_encounter_id`, `hint_encounter_game_id`, `workspace_id`, `requested_by_user_id`, `status`
  (`pending|done|failed`), `attempts`, `next_attempt_at`, `last_error`, `ingest_job_id`, `created_at`, `updated_at`.
  Unique `uq_match_fetch_game (source_kind, external_id, hint_encounter_game_id)`.
* **Routes** (tournament-service, which authorizes the caller and names the game; stats-service owns the request):

  | Route | Subject | Who |
  | --- | --- | --- |
  | `POST /api/v1/encounters/{encounter_id}/games/{game_id}/match-import` | `rpc.tournament.captain_match_import` | A captain of the encounter (else 403) |
  | `GET /api/v1/encounters/{encounter_id}/games/{game_id}/match-import` | `rpc.tournament.captain_match_imports` | The same |
  | `POST /api/v1/admin/encounters/{encounter_id}/games/{game_id}/match-import` | `rpc.tournament.admin_match_import` | `match.result` |
  | `GET /api/v1/admin/encounters/{encounter_id}/games/{game_id}/match-import` | `rpc.tournament.admin_match_imports` | `match.read`; the only read with warnings |

  * Body `{"external_id": "<match id>"}`. A row is `{id, status, attempts, last_error, external_id, created_at,
    warnings}`; the GET is a bare array, newest first.
  * They forward to the internal `rpc.stats.ingest.fetch` and `rpc.stats.ingest.fetch_list` (no gateway route) and
    relay the stats reply verbatim. When stats does not answer: 503 `unavailable`.
* **Refusals:**

  | Code | When |
  | --- | --- |
  | 422 `match_import_tournament_only` | A mix encounter or a scrim container |
  | 404 | A game of another encounter, or a cancelled game |
  | 422 `unsupported_ingestor` | The encounter's discipline declares no fetcher |
  | 422 `invalid_external_id` | Not 1–128 of `A-Z a-z 0-9 _ . : -` |
  | 409 `match_already_imported` | Another game of the workspace holds the same id, not failed |

  The same id for the same game returns the existing row; a failed one is reset to `pending` with a fresh 24 h
  window.
* **Worker tick:** every 60 s, leader-locked on `stats:match_fetch:leader:<disciplines>`, `stats-worker` tries up to
  20 due `pending` rows of the disciplines it serves. It runs only when one of them has a fetcher.

  | Fetcher result | Effect |
  | --- | --- |
  | Bytes | Stored and queued exactly like an upload (`logs/{tournament}/{sha256}`, the normal ingest job with the game hint); `done`, `ingest_job_id` set |
  | `MatchFetchNotReady` or any other exception | Backoff 1, 2, 5, 10, 20, 40 min, then hourly; `last_error` says why |
  | Still not ready 24 h after the request | `failed`, `not_available_after_24h: <reason>` |
  | `MatchFetchFailed` | `failed` at once |
  | Larger than `MAX_MATCH_LOG_BYTES` | `failed`, `match_too_large` |
  | The ingest job key refuses the bytes | `failed` with that code (for example `idempotency_conflict`) |

* **Deadlock's fetcher** (`fetch.py`): `GET /v1/matches/{id}/metadata`. deadlock-api serves a match once its replay
  is parsed (private lobbies included). 404, 429, 5xx and transport failures → not ready. A non-numeric id, any
  other non-200, or a 200 without `match_info` → failed.
* **Warnings**, derived when the organizer reads the list, never stored:
  * `fetch_failed`: the row gave up (`last_error` says why);
  * `participants_dropped` (`count`): over the bound observation's teams, the sum of `max(0, format starters −
    players seen)`. This is what a decoder dropping anonymous accounts leaves behind;
  * `banned_character_played` (`characters`): the observation's characters that the game's hero room banned for that
    game (`round` = game position, carried bans included).
* **Capability:** `DisciplineCapabilities.match_fetch` = the discipline declares a fetcher. The frontend shows match
  import only when it is true. Today only Deadlock has it.

## 4. Migration `deadlock01`

`cd backend && uv run alembic upgrade head` → `deadlock01 (head)`. `deadlock01` makes these changes:

* inserts `catalog.discipline ('deadlock', 'Deadlock')` (`ON CONFLICT DO NOTHING`);
* seeds `public.settings` `deadlock.rank_collection` with the collector's defaults (`enabled: true`, interval 21 600,
  `batch_size` 1000, scope `all`, …; no `rate_limit_per_minute`, so it follows `DEADLOCK_API_KEY`), `ON CONFLICT DO
  NOTHING`;
* creates `stats.match_fetch` with these foreign keys: `workspace_id`, `hint_tournament_id`, `hint_encounter_id` and
  `hint_encounter_game_id` ON DELETE CASCADE; `requested_by_user_id` → `auth.user` and `ingest_job_id` →
  `stats.ingest_job` ON DELETE SET NULL; `discipline` → `catalog.discipline`. Indexes: `uq_match_fetch_game`,
  `ix_match_fetch_due (status, next_attempt_at)`, `ix_match_fetch_workspace_external (workspace_id, source_kind,
  external_id)`.

**Downgrade** (`alembic downgrade drift01`) drops `stats.match_fetch`, the settings row and the discipline row. A
database that already holds Deadlock data (tournaments, catalog rows, rank rows) refuses the discipline delete by
foreign key: that data is never dropped silently.

The generated schema docs (`backend/docs/schema.dbml`, `schema.sql`, `docs/database_erd.md`, the site's
`schema.generated.json`) include `stats.match_fetch`.

## 6. Operator steps

1. Run the migration, then deploy every image from the same SHA (section 4).
2. Steam: set `STEAM_OAUTH_ENABLED=true` in `auth.env`. There is no developer console and nothing to register; Steam
   shows the realm (`https://owt.craazzzyyfoxx.me`) on its sign-in page. See
   [workspace-domains.md](../workspace-domains.md#steam-openid-20).
3. Optional: set `DEADLOCK_API_KEY` in `stats.env` for the per-key rate limits.

## 8. Deferred

* **No Redis in-flight dedup** in the Deadlock collector (marked `ponytail:` in `enqueue_fetch`): a duplicate fetch
  costs one request, and a race can write one duplicate snapshot row.
* **Import warnings live only on the organizer's match-import list**, not in the room history: stats must not write
  `encounter.*`, and journaling would need a new event, queue and consumer.
* The import row does not echo the ingest job's own outcome (`awaiting_link`, `failed`); the admin log monitor shows
  it.
* **Mode is not carried:** `MatchDoc` has no mode field, so an imported Deadlock match has no `normal`/`street_brawl`.
* **No database end-to-end run of the fetch tick:** the test stack has no S3, so the store-and-queue path was not run
  against a database.
* `in_development` heroes (hero labs) appear in the catalog and the ban pool.
* The rated role `agent` ("Agent") is outside the D99 role vocabulary; renaming it is a label change only.
* A vanity Steam link (`/id/<name>`) is not resolved.
* Out of scope: Discord bot lobby creation, and the Deadlock profile statistics, leaderboards, achievements and
  analytics.
