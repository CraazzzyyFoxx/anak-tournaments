# Промт для запуска реализации (вставить целиком)

```
Реализуй редизайн публичной страницы турнира по плану docs/tournament-redesign/plan.md. Работай в режиме оркестратора с сабагентами.

Модели: ты — оркестратор на текущей модели сессии; все сабагенты P2–P7 — Opus. Это задано в ~/.omp/agent/config.yml (task.agentModelOverrides.task = anthropic/claude-opus-5:high), запускай их агентом `task`, не `sonic` и не `scout`. Перед батчем убедись, что override действует (первый сабагент в отчёте называет свою модель).

Перед началом прочитай целиком, в этом порядке: docs/tournament-redesign/plan.md; docs/tournament-redesign/wireframes.html (открыть в браузере — там 11 секций с нумерованными заметками, план ссылается на них как «§3 ⑤»); frontend/DESIGN.md; docs/design-book.md. Таблицу «Данные, которые уже есть» в §0 плана — принять как факт и не переискивать.

Порядок работы строго по плану:

1. P0 и P1 делаешь сам, последовательно, в одной ветке от develop. Это контракты (роуты, URL-параметры, пропсы общих компонентов из §1.3), от которых зависят все сабагенты. Пропсы общих компонентов — ровно как в §1.3; если что-то надо изменить — измени §1.3 в plan.md тем же коммитом, чтобы сабагенты читали актуальную версию. После P1: typecheck по затронутым файлам, vitest по затронутым тестам, коммит «feat(tournament): shell + shared components (P0, P1)».

2. P2–P7 запускай одним батчем как шесть параллельных сабагентов A–F по таблице §3 плана. Каждому — полный самодостаточный task: его WU из §2 дословно, его список файлов из §3 (владеет / читает), ссылка на секцию wireframes и её заметки, контракт §1.3 и §1.2, DoD из §0. В общем контексте батча: «работать от коммита P1; не трогать файлы вне своего списка; в i18n/messages/{ru,en}.json добавлять ключи только в своём неймспейсе; не запускать полный typecheck/vitest/build — только по своим файлам; не коммитить; не оставлять заглушек, TODO, плейсхолдеров, мок-данных; если данных нет — честное пустое состояние через TournamentPageState; если из плана что-то непонятно — спросить через hub у Main, не угадывать». Сабагент F (P7, админка) не зависит от P0/P1 и может стартовать первым, до окончания P1.

3. По завершении каждого сабагента — проверь его изменения сам, не доверяй отчёту: открой файлы, прогони его тесты, посмотри экран в браузере на 1440 и 375. Отклонения от wireframes без причины в коде — вернуть сабагенту с конкретным списком. Мерджи по одному WU, коммит на WU.

4. P8 делаешь сам: удаление старых роутов и вью, мобильная сетка, полный typecheck + vitest + next build, браузерная проверка каждого раздела в трёх статусах турнира на 375/768/1280/1440 (одна sticky-полоса под хедером сайта, scrollWidth <= innerWidth, все интерактивы с accessible name). Факт про sticky-рейл — в Graphiti.

Жёсткие границы: bracket/TournamentBracketPage.tsx и BracketView.tsx не менять (разрешены только ?match= и ?view= из §4 плана и обёртка для мобильного из P8). VirtualParticipantsList.tsx — только гейт колонок. Backend не трогать — всё нужное уже в API (§4 плана). Новые npm-зависимости не нужны. Все команды через rtk.

Финальный отчёт: список WU с коммитами; что отклонилось от wireframes и почему; что проверено в браузере и на каких статусах турнира; что осталось (если осталось — это не «done», а список блокеров с тем, что именно пробовал).
```
