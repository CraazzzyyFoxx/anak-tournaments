# Admin shell & shared vocabulary inventory

Scope: `frontend/src/app/admin/layout.tsx` + `AdminLayoutClient.tsx`, `frontend/src/components/admin/*` shared primitives, `components/ui/sidebar.tsx` API surface, admin-related scopes of `globals.css`, `tailwind.config.ts`. Read-only inventory for an IA redesign.

## Shell layout

**`app/admin/layout.tsx`** (server component) reads the `admin` sidebar-open cookie (`SIDEBAR_COOKIE_NAMES.admin`) and passes `defaultSidebarOpen` into `AdminLayoutClient`. No other server work.

**`AdminLayoutClient.tsx`** (`"use client"`) is the entire shell:
- Gate: `usePermissions().isLoaded` → `LoadingState` (centered spinner); route permission check against `getMatchingAdminRoute(pathname)` (fallback to `adminEntryPermissions`) → `UnauthorizedState` (centered block with "Go Home" link) if denied. Both states short-circuit before the shell renders — no `<AdminSidebar>` mount on unauthorized.
- `TooltipProvider delayDuration={300}` wraps everything (every `StatusIcon`/tooltip in the tree shares one delay).
- `SidebarProvider` (from `components/ui/sidebar.tsx`) owns open/collapsed state, seeded from the cookie, with `cookieName={SIDEBAR_COOKIE_NAMES.admin}` so toggling persists server-side. Custom CSS vars set inline: `--sidebar-width: 15.5rem`, `--sidebar-width-icon: 3.75rem` (overrides the component's own 16rem/3rem defaults).
- Skip-link (`#admin-content`) precedes the sidebar in DOM order — the only accessibility affordance for bypassing ~30 nav links.
- `<AdminSidebar />` (see below), then `<SidebarInset className="min-w-0">` holding:
  - Sticky header bar: `h-12`, `sticky top-0 z-20`, blurred translucent background (`bg-background/90 backdrop-blur`), containing `SidebarTrigger` (toggle button) + vertical `Separator` + `AdminBreadcrumb`.
  - Content container: `id="admin-content"`, `flex flex-1 flex-col gap-4 overflow-x-hidden p-4` — **no max-width constraint**, just `p-4` padding; pages fill the full inset width.
  - `AuditTrailProvider` wraps `children` — one global audit-trail sheet/drawer for the whole panel (pages never mount their own).

**Breadcrumb logic** (`AdminBreadcrumb`, defined inline in `AdminLayoutClient.tsx`): splits `pathname` on `/`, first segment always renders as "Admin" (linked to `/admin`), each subsequent segment becomes a crumb via `formatBreadcrumbLabel` (kebab→title case; a purely-numeric segment becomes literal "Details"). `getBreadcrumbEntityRef` special-cases `/admin/tournaments/:id` and `/admin/teams/:id` to resolve the numeric id against the React Query cache (`skipToken` — read-only, never fetches) and show the entity's real name instead of "Details", falling back to the formatted label if the cache is cold. No other entity types get name resolution (e.g. `/admin/players/:id`, `/admin/access/users/:id` — if they exist — show "Details").

**Where page headers live**: not in the shell. Every page renders its own `<AdminPageHeader>` (see below) as the first element inside `#admin-content`; the shell only supplies the breadcrumb above it.

## Page header — `AdminPageHeader.tsx`

Single-purpose primitive: owns the page's one `<h1>` (explicit fix for a prior bug where hand-rolled headers shipped with no heading element).

Props: `title` (string, required), `description?` (string, muted line under title), `actions?` (ReactNode, right-aligned button/link cluster), `meta?` (ReactNode, inline next to title — badges/counts), `titleHidden?` (bool, renders `<h1 className="sr-only">` — for pages whose breadcrumb already shows the same name), `footer?` (ReactNode, full-width line below the header row — used for extra counts/dates).

Layout: `title`+`meta` on one line (`h1` truncates with a `title` attribute tooltip), `description` truncates below it, `actions` float right and wrap onto their own row only if title+meta already consumed the row (`flex-1` on the text block keeps actions pinned). No breadcrumb, no sticky behavior, no tabs — it is a static header block, not a mini shell. No slot for a search bar or filter row; those live inside `AdminDataTable`'s own toolbar or bespoke page markup below the header.

30+ admin pages import it directly; it's the single most-reused primitive after `AdminDataTable`.

## Data table — `AdminDataTable.tsx` (987 lines — largest file in this inventory)

Generic `<TData>` component built on TanStack Table. Two mutually exclusive data modes:
- **Server mode**: `queryKey`/`queryFn` callbacks receive `(page, search, pageSize, sortField, sortDir, filters)` and return `PaginatedResponse<TData>` — the table drives pagination/sort/filter entirely via server round-trips (React Query).
- **Client mode**: caller passes `rows: TData[]` (+ optional `isLoading`) — search/sort/filter/paging all run in-memory via TanStack's row models.

Props surface (grouped):
- **Data**: `queryKey`, `queryFn`, `rows`, `isLoading`, `columns` (required `ColumnDef[]`).
- **Search**: `searchPlaceholder` (debounced 300ms via `use-debounce`).
- **Sort**: `initialSort: { field, dir }`.
- **Filters**: per-column filters declared on `columns[].meta` (read via `admin-table-columns`/`admin-table-filters` helpers), rendered as a funnel-icon popover (`AdminColumnFilter`) beside each sortable header; `filterKey` (opaque cache-buster string that resets to page 1 on change — for caller-owned filters like chips); `filters`/`onFiltersChange` for controlled mode (e.g., a "49 pending" chip driving the table from outside).
- **Selection**: `getRowId` (required for stable selection across refetch), `enableRowSelection: (row) => boolean` (adds leading checkbox column; a row can opt out), `bulkActions: (selected, clearSelection) => ReactNode` (rendered in toolbar only while ≥1 row selected).
- **Expansion**: `renderExpanded: (row) => ReactNode` (adds leading chevron, expands a full-width detail row).
- **Grouping**: `groupRows: (rows) => AdminDataTableGroup[]` (splits the current page into labelled sub-groups with a header row each — client-side visual grouping, not a TanStack grouping model).
- **Columns picker**: `columnsStorageKey` (shows a "Columns" dropdown, persists visibility to localStorage; only columns declaring `meta.category` — `core`/`meta`/`admin` — are offered).
- **Row interaction**: `onRowClick`, `onRowDoubleClick` (keyboard-reachable via `tabIndex=0` + Enter, with an `sr-only` hint).
- **Toolbar extra**: `actions` (arbitrary ReactNode, e.g. a `TournamentFilterSelect` or `AdminFilterChips`).
- **Density/appearance**: `cellAlign: "top" | "middle"` (top for wrap-prone cells), `paging: "pages" | "infinite"` (infinite is client-mode-only, uses `InfiniteScrollFooter` + Load-more instead of numbered pages), `rowUnit` (plural noun for infinite footer), `initialPageSize`/`pageSizeOptions` (default `[10,15,25,50,100]`, default page size 15), `emptyMessage`.

Toolbar (top, `border-b`): search input (left) + optional refreshing spinner, then bulk actions / columns picker / `actions` slot (right) — all in one row, no wrapping to a second toolbar row.

Header row: sticky-left support for pinned columns (`admin-sticky-col` class + inline `left` style) computed from column meta; per-column sort toggle (click header text) with a separate funnel button for filtering (deliberately split targets, "the same split antd's table header uses").

Body: optional grouped section headers; row hover/selection states; the trailing "actions" column (id `"actions"`) is hidden until row hover/focus (`opacity-0` → `opacity-100` on `group-hover`/`focus-within`) — **primary row actions are invisible until interaction**, a pattern repeated on every CRUD table.

Footer: page-mode shows a numbered pager (max 5 visible page buttons with `…` gaps) + a per-row-count Select; infinite-mode shows `InfiniteScrollFooter` instead. No pagination footer at all when `safeTotal === 0`.

Empty state: centered icon + `emptyMessage`, plus a contextual "Clear search"/"Clear filters"/"Clear search and filters" button only when a search or filter is currently active.

No column reordering, no CSV export, no server error state distinct from empty (loading vs. zero-results vs. fetch-error are not visually distinguished beyond the refresh spinner).

## Tokens & type

- **Font stack** (`tailwind.config.ts`): `sans` = Inter (`--font-inter`), `mono` = JetBrains Mono (`--font-jetbrains-mono`), `display`/`onest` = Onest with Inter fallback (`--font-onest`) — used for page-hero/display titles, not body text. Admin body/table text uses the default `sans` (Inter); numeric columns get `tabular-nums` utility, not the mono font, in `AdminDataTable`/`StatTile`.
- **Sidebar tokens** (`globals.css`, declared on `.dark`, not `:root` — deliberate, so per-tenant `WorkspaceThemeSync` overrides on `<body>` are visible): `--sidebar`, `--sidebar-foreground`, `--sidebar-primary`, `--sidebar-primary-foreground`, `--sidebar-accent`, `--sidebar-accent-foreground`, `--sidebar-border`, `--sidebar-ring` — every one aliases an `--aqt-*` token (e.g. `--sidebar: var(--aqt-bg-2)`, `--sidebar-primary: var(--aqt-teal)`). Exposed to Tailwind via `@theme inline` as `--color-sidebar-*` → utilities like `bg-sidebar`, `text-sidebar-foreground`, `border-sidebar-border`. The admin panel is the **only** sidebar consumer in the app (one color scheme, no light/dark split).
- **`--aqt-*` redesign token layer** (globals.css, declared on `:root`, dark-only app): surface ladder `--aqt-bg` → `--aqt-bg-2` → `--aqt-card` → `--aqt-card-2`; border ladder `--aqt-border` → `-2` → `-3`; text ramp `--aqt-fg`, `--aqt-fg-dim`, `--aqt-fg-muted`, `--aqt-fg-faint`; brand/result hues `--aqt-teal`, `--aqt-emerald`, `--aqt-amber`, `--aqt-rose`, `--aqt-violet`, `--aqt-blue`, `--aqt-gold/silver/bronze`; role hues `--aqt-tank`, `--aqt-damage`, `--aqt-support` (intentionally distinct from the rose/teal result hues — "Results ≠ roles" per inline comment); font vars `--aqt-mono`, `--aqt-display`. Exposed to Tailwind as `colors.aqt.*` (`aqt-teal`, `aqt-tank`, etc.) and directly to legacy medal colors (`firstPlaceBg`, `secondPlaceBg`, `thirdPlaceBg`).
- **shadcn semantic tokens** (`--background`, `--card`, `--border`, `--primary`, `--muted`, `--accent`, `--popover`, `--destructive`) are mapped onto the same `--aqt-*` palette so every shadcn component renders in-brand.
- **Tone roles for admin status surfaces** (`success`/`warning`/`info`/`danger` in `tailwind.config.ts`, backed by `--success`/`--warning`/`--info`/`--danger` in globals.css): full-opacity for text/borders, low-alpha (`/10`) for tinted surfaces — this is the *actual* token set `tone.ts`'s `TONE_CLASS`/`TONE_TEXT` index into, plus a `neutral` and `accent` (primary-based) tone that have no dedicated CSS custom property (they reuse `--muted`/`--primary`).
- Container: Tailwind's default `container` centers with `2rem` padding but **`AdminLayoutClient` never uses the `container` class** — admin content is `p-4` full-width inside the sidebar inset, not the same max-width system as the public site (which does use `container`/`max-w-screen-3xl` elsewhere per `tailwind.config.ts`'s `maxWidth["screen-3xl"]`).

## Command palette

`AdminCommandPalette` scope is **pages only** — it indexes `AdminNavGroup[]` (the static nav config), not entities. Search haystack per item = `title + description + aliases` (`adminNavItemSearchValue`). Some pages register extra `aliases` to catch entity-ish queries that resolve to that page (e.g. "discord"/"battletag"/"twitch" → Player identities page; "staff"/"roles"/"permissions"/"api keys" → Staff access page) — but there is no live entity search (no jumping straight to a specific team, tournament, or user by name/id from the palette). Triggers: `Ctrl+K`/`Cmd+K` (toggle) and bare `/` when focus isn't in a text field. Screen-reader result count is announced via a `role="status"` live region reading cmdk's internal filtered count.

## Cross-screen observations

1. **Two competing "actions column" conventions coexist by design**: `row-actions-column`'s `createRowActionsColumn` (edit+delete icon pair, per-permission gates) for encounters/players/standings, vs. `catalog-table-columns`'s `createEntityActionsColumn` (single dropdown, `isSuperuser`-gated) for heroes/maps/gamemodes. A redesign should either unify these or make the split intentional and visible (e.g. "CRUD tables" vs. "catalogue tables" as a named IA distinction), since visually they will read as inconsistent to a user who doesn't know two systems exist.
2. **Two competing "toolbar filter" widgets for the same slot**: `TournamentFilterSelect` (a `<Select>` dropdown) is the de facto standard (encounters, players, standings, teams), while `AdminFilterChips` (pill row) exists for exactly this purpose but has only 1 adopter (`ParsedMatchesBrowser`). A wireframe pass should pick one visual language for "filter this table by X" and retire the other, or document when each applies (single-value exclusive filter vs. multi-value).
3. **Primary row actions are hidden until hover/focus** in `AdminDataTable` (`opacity-0` → `opacity-100` on hover/focus-within for the trailing actions column). This is consistent within the table but means every list screen's primary actions (edit/delete) are undiscoverable without hovering — a mouse-only affordance despite keyboard focus also revealing it. Worth flagging for the redesign: either make actions always-visible at lower opacity, or add a visible "..." affordance.
4. **`StatTileGridSkeleton` loading-state coverage is inconsistent**: used by stream-health and subscription-health (2 of 3 "collector health dashboard" pages) but not by rank-health, despite all three sharing the `StatTile`/`StatTileGrid` pattern and the doc comment's claim it's "shared by every collector's health dashboard."
5. **`TintedBadge` is under-used relative to its stated scope**: its doc comment claims it's for "every admin collector (rank, subscriptions, streams)" but only `rank-shared.tsx` imports it — subscriptions/streams reach for `TONE_CLASS` directly instead, producing near-identical badges through two different code paths.
6. **No page-level max-width/container**: the admin content area is edge-to-edge (`p-4` only) inside the sidebar inset, unlike the public-facing site which uses Tailwind's `container`/`max-w-screen-3xl`. On very wide viewports, `AdminDataTable`'s columns and `AdminPageHeader`'s single-line title can stretch further than intended — worth an explicit decision in the redesign (keep full-bleed, or introduce a `max-w-screen-2xl` wrapper).
7. **Breadcrumb entity-name resolution is special-cased to exactly two routes** (`/admin/tournaments/:id`, `/admin/teams/:id`); every other detail route (players, users, achievements, workspaces, encounters) shows the generic "Details" crumb instead of the entity's name — an inconsistency a redesign's IA should either generalize (a shared "detail route → query key" registry) or explicitly scope down.
8. **Nesting depth**: Shell (sidebar + breadcrumb) → page (`AdminPageHeader` + toolbar/filters) → `AdminDataTable` (search + column filters + bulk actions + columns picker, all in one toolbar row) → row-level `EntityFormDialog`/`DeleteConfirmDialog` (modal) → within some entity dialogs, nested comboboxes (`TeamCombobox`, `UserSearchCombobox`) open their own popover. That's shell → header → table-toolbar → dialog → combobox-popover, a 4–5 level stack on the busiest CRUD pages (encounters, players). `AuditTrailProvider`'s sheet adds one more overlay layer that can open from *any* depth in that stack (it's a single global instance, not owned by any screen).
9. **`AdminDataTable` at 987 lines is the single largest complexity concentration** in the shared vocabulary — it owns data-fetching (2 modes), search, sort, filter (2 systems: header-cell filters + caller-owned chips/selects), selection, expansion, grouping, column visibility, and two pagination modes in one component. A redesign that simplifies table behavior (e.g., picking one filter system, one pagination mode) would shrink this file substantially and reduce the number of props a wireframe needs to account for per screen.
10. **Command palette has no entity search**, only page search — for an admin with heavy entity-centric workflows (find this team, this player, this tournament), users must first navigate to the right list page and then use that page's own search box; a redesign candidate is extending the palette to entities (would require a backend search endpoint per entity type, a bigger scope than the current pages-only palette).
